# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Butler** is a household concierge - a shared-tablet family operating system, built as a tech
experiment and #buildinpublic series. The v1 scope is a hard line; when in doubt, do not expand it.
Only open the [Product Vision](Butler.KnowledgeBase/docs/10-product-vision.md) for a product or
scope question, and then only the section you need (for scope, its "What we are NOT building in v1").
For implementation work the principles below plus the Engineering Contract are sufficient.

  7.3 Table Storage keyed by `householdId`, 7.4 organizer auth + tap-to-claim, 7.5 RFC 7807 / optimistic

## Monorepo shape

Three independent sub-services, each with its own build, deploy, and `infra/`. No root build - operate
inside the relevant folder.

- `Butler.UI/` - Expo (React Native + react-native-web), **web-first**: the v1 hub is the Expo web
  export deployed as an Azure Static Web App (installable PWA). Has its own `AGENTS.md`.
- `Butler.API/` - .NET 10 Web API (`Butler.API.sln` -> `src/Butler.Api`), deployed to Azure App Service.
- `Butler.KnowledgeBase/` - **agent-managed** wiki (see "Working in the knowledge base"). Not product code.

`I<Feature>Service` -> `I<Feature>Repository` -> Table Storage.

| Where | What |
| --- | --- |
| `Butler.Api/Program.cs` | Composition root. One `services.Add<Feature>Feature()` call per feature. |

| `Butler.Api/Infrastructure/<Feature>/` | `<Noun>Entity.cs` (table entity), `I<Noun>Repository` + `Table<Noun>Repository`. |
| `Butler.Api/Infrastructure/Storage/` | Shared persistence seam: `AddStorage()`, `AddTableRepository<TEntity>("<Table>")`, `TableEntityRepository`, `InMemoryEntityRepository` (auto-used and auto-seeded when no storage is configured). `SeedData/grocery/` is the simulated store catalog. |
| `Butler.Api/Infrastructure/Auth/` | Organizer (JWT + dev bypass), participant session (tap-to-claim), and hub-device auth handlers. |
| `Butler.Api/Application/Concurrency/` | Optimistic-concurrency helpers and exceptions (ETag / If-Match). |
| `Butler.Api/Mediation/ApiExceptionHandler.cs` | Maps exceptions to RFC 7807 problem details. |
| `Butler.Api/Domain/` | Small pure domain types (`Scheduling/WeekIso`, `System/`). |
| `Butler.Api.Tests/<Feature>/` | xUnit + NSubstitute. Service unit tests plus endpoint tests through `TestSupport/ButlerApiFactory` (real `Program`, Development env, dev organizer injected). |

## Commands

Prefer the quiet forms shown; drop the flags only when you need the detail to debug a failure.

Butler.UI (from `Butler.UI/`):
```bash
npm ci --no-audit --no-fund --loglevel=error
npm run web                      # web-first dev loop (the hub in a browser)
npm run build:web                # deployable PWA export -> dist/ (NOT a bare `expo export`)
npm run ci:verify                # CI gate: lint + typecheck + 98% coverage-gated jest
npx jest --silent path/to/File.test.tsx                               # one test file
npx jest --coverage --silent --coverageReporters=text-summary         # coverage totals only
```

Butler.API (from `Butler.API/`):
```bash
dotnet restore -v q --nologo
dotnet build --nologo -v q -clp:ErrorsOnly         # CI also passes /p:TreatWarningsAsErrors=true
dotnet test --nologo                               # xUnit suite
dotnet test --nologo --filter "FullyQualifiedName~Rooms"   # one feature's tests
dotnet test --nologo /p:CollectCoverage=true       # + enforce the 98% gate (Contract 7.7)
dotnet run --project src/Butler.Api -- --urls http://localhost:5108
dotnet test --nologo src/Butler.Api.SmokeTests   # smoke suite (needs API + Azurite running; see README)
```

Infra (both services) - Bicep, deployed per-service:
```bash
az deployment group create -g <rg> \
  --template-file <service>/infra/main.bicep \
  --parameters <service>/infra/main.bicepparam
```

## Architecture principles (from the vision - keep these true)

- **The household model is the shared spine.** Rooms, people, and chores are the core entities every
  capability reads from and writes to.
- **Each capability is a module** (chores, groceries, calendar, ...) on top of that spine, independently
  launchable - modularity is a go-to-market asset.
- **Grocery integration is a generic store-connector abstraction**, HEB first (simulated; HEB has no
  public consumer API). Never hard-wire a single store into product logic.
- **Multiplayer is the whole game.** Hub + no-password tap-to-claim; do not reintroduce per-user login
  friction on the shared device.

## Azure resource naming

`infra/` Bicep templates are **policy-agnostic**: names and tags are parameter-driven and the committed
`.bicepparam` values are placeholders. For a Frontier Energy subscription, generate compliant
names/tags with the `azure-resource-naming` skill rather than hand-authoring them.

## Working in the knowledge base

`Butler.KnowledgeBase/` is an [OKF v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md)
bundle (ADR-0011): one concept per file, each with `type` and a one-sentence `description` in its
frontmatter. To find a file without opening any, run `grep -rh "^description:" Butler.KnowledgeBase`, or
read `index.md` (root) and `brd/index.md`. Do not read `intake/` (raw provenance). In `docs/`, articles
are graph nodes with bidirectional `related:` edges; every write there is a graph edit (index entry,
reciprocal edges, `generated:` on meaningful changes). The rules are in `HOW-TO-MAINTAIN.md`. Use the
`knowledge-base` skill for any non-trivial change. Plain ASCII only - no em dashes, curly quotes, or
ellipsis (the usability scorer hard-fails them).

**Demo push (temporary; decided in #143 on 2026-11-13).** Until the demo ships, a ticket updates only the
code-adjacent docs its change touches (READMEs, `ARCHITECTURE.md`) and skips full knowledge-graph edits:
no writes to `docs/`, no new or amended decision records in `adr/`, and no `knowledge-base` skill run.
The exception is a docs ticket (an issue labeled `area:docs`), which follows the full process above.
**Ends when the demo ships:** delete this paragraph, and the full process applies to every ticket again.
